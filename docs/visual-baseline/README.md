## 実行方法

`npm run dev` と、リモートデバッグ用ポートを 9234 にした別プロファイルの Chrome を起動する。`node scripts/check_visual_frames.mjs` で各定点の直接シーク、1刻みずつ更新、4刻みずつまとめて更新、逆戻りを比較する。`--video` で短縮した65コマのMP4を2回書き出し、全コマとスタート地点の直接シーク画像を照合する。

通常の書き出しで各フレームのハッシュを確認する場合は、開発環境のコンソールで `window.paddockExportHashes = []` を設定してから書き出す。`window.paddockFailAt = 3` を設定すると4コマ目でエンコーダーを閉じ、失敗時の復帰を検証できる。次回の書き出し前に `delete window.paddockFailAt` で解除する。

開発ページ `/visual-check` の `captureRaceFrame(options)` は検証用 canvas を返す。入力には `raceId`, `progress`, `speed`, `cameraMode`, `selected`, `width`, `height` を指定する。`fixed` は `{position, target}`、`quality` は `preview` または `export`、`composite` は下段を含める指定。`history` には描画を挟まずに通る再生位置を並べる。

Chrome の標準キャンバスで数画素の丸め差が生じたため、ハッシュ検証は単一サンプルのフレームバッファーから取得する。プレビューはGPUのアンチエイリアス、書き出しは縦横2倍からの縮小を使う。書き出しの合成には毎回同じ Canvas 2D バックエンドを使う。

MP4 の格納には Mediabunny 1.66.0（MPL-2.0）を使用する。対応ブラウザーでは途中のエンコードデータを Origin Private File System に逐次書き込み、完了後にダウンロード用の Blob にする。

[Mediabunny パッケージ](https://www.npmjs.com/package/mediabunny)

RTX 3070、Chrome 157の試験では、エリザベス女王杯・再生倍率2・高低差4倍の全3,983コマを約229秒（動画長の約3.5倍）で書き出した。保存した MP4 は1920×1290、60fps、66.383秒、平均23.59 Mbps。試験動画は `queen-elizabeth-export-4x.mp4`。途中でChromeを裏タブにした18秒間に679コマから973コマへ進み、保存まで完了した。Chromeタスクマネージャーでのメモリ差分とフルレース全コマのハッシュ一致は未計測。

## 京都の試行

高さを測定点間で傾きが連続する周期補間に変更した。京都は依頼者が選んだ4倍を用いる。比較画像は定点3の同一の進捗、カメラ、モデル予想で撮影した。

| 対象 | 公式一周 | 現在の平面弧長 | 差 | 公式最終直線 |
|---|---:|---:|---:|---:|
| 芝・内回り | 1782.8 m | 1782.80 m | 0.00% | 328.4 m |
| 芝・外回り | 1894.3 m | 1876.94 m | −0.92% | 403.7 m |

[JRA 京都競馬場コース紹介](https://www.jra.go.jp/facilities/race/kyoto/course/)

外回りは一周距離の許容誤差±0.5%を超える。平面の線形と接合面は試行を継続する。先に共有する直線と内ラチを固定し、分岐から合流までの曲率・接線を合わせながら公式弧長と直線長に合わせる。その座標を使って引込線を再接続し、走路の境界で面を切り分ける。`kyoto-plan-overlay.png` と `kyoto-curvature.png` は現行線形の基準。曲率がゼロになる最終直線の起点は新しい線形で測る。

掲載中の京都2レースは高さのみの変更なので、平面のコーナー位置と発走地点の誤差は改修前後で同じ。発走地点の誤差はエリザベス女王杯が7.67m、天皇賞（春）が0.96m。

適合・計測の自動化に1〜2作業日、引込線と面の接合および全レースの検証に2〜3作業日を見込む。B-試行の検収後に他場へ展開する。

## 京都の線形の定義し直し(B-1)

`app/alignmentData.ts` に、京都の内回り・外回りを直線・緩和曲線・円弧の並びとして持たせた(`scripts/fit_alignment.mjs` で案内図に当てはめ、`scripts/write_alignment.mjs` でデータ化)。一周は公式値に厳密(内回り 1782.8 m、外回り 1894.3 m、曲線長との差 0.03 m 以内)、最終直線は内回り 328.4 m・外回り 403.7 m。ゴールからの共有区間(ホームストレッチ、1〜2角、向正面の途中まで)は同じ要素を参照するのでずれ 0。外回りは案内図どおり、内回りの直線へ緩い S 字で合流する。

案内図との重ね合わせは、内回りが平均 4.9 px(最大 11.6 px)、外回りが平均 5.1 px(最大 14.9 px)で、許容の 3 px を超える。公式の一周・直線長を優先し、案内図の縮尺も当てはめに含めたため(2.009 → 約 2.03 m/px)。許容内に収める方法の検討は未了。

外回りの高低は、走路が重なる範囲の合成幅を 18〜34 m から 6〜16 m に狭めて 3.97 m(公式 4.3 m)。重なる区間の段差は B-5(面を1枚につなぐ)で解消する。`check_geometry`・`check_camera`・`check_finish`・`check_pace`・`check_passing` は通る。`check_replay` は着手前から失敗している。
